## Corrections par rapport au plan (faits du dépôt qui contredisent §5 « Lot 2 »)

1. **Un seul système de pointage est vivant côté soignant.** Le plan (l.62, l.180, l.183) exige les « deux systèmes QR ». Depuis la PR #664 (`1879ed65`, 22/06/2026), le seul composant monté est `PointageRotatifSoignant` (`src/components/pointage/PointageRotatifSoignant.tsx`), via `BlocPointageMission` (`src/components/pointage/BlocPointageMission.tsx` l.69-70) dans `PresencesSoignant.tsx` l.634-639 et l.657-662. `pointerArrivee` (`PresencesSoignant.tsx` l.365-443) et `pointerDepart` (l.445-512) ne sont appelés nulle part ; `CartePointage`, `ScannerQRPointageSoignant`, `QRPointageEtab`, `SaisieCodeSecours` ne sont montés par aucune page (seul `CartePointage.tsx` les importe) ; `SaisieCodePointage` est importé (l.9) mais jamais rendu ; `src/lib/qr-offline-queue.ts` n'est importé que par `CartePointage.tsx` l.14. `docs/POINTAGE_DIAGNOSTIC.md` classe ce système ① comme à retirer (« PR 5 »). Côté établissement, l'écran monté est `AffichageCodeRotatifEtab` (`DetailPresencesMission.tsx` l.494, `DetailMission.tsx`), dont le QR encode `code_pointage_actif` (`AffichageCodeRotatifEtab.tsx` l.284 `QRCodeSVG value={code}`), pas un jeton de `fn_generer_qr_mission`. Porter ① ajouterait un chemin qui contourne le contrôle « contrat signé » (`fn_valider_scan_qr` l.65545-65710 ne le vérifie pas, contrairement à `fn_scanner_code_pointage` l.55671-55678) et bloque les missions multi-jours (« Vous avez déjà pointé votre arrivée », l.65608-65611). → §7 Q1.
2. **La file hors-ligne de `qr-offline-queue.ts` est un renvoi automatique** (écouteur `online` et Capacitor l.120-145, trois relances l.86-93), contraire à PRINCIPES §4 l.53-55. Elle n'existe que pour ①. Le système vivant horodate au serveur (`v_now := now()`, l.55628, corrigé v2 ; `scanne_le = v_now`, l.55718-55735) : un code rejoué plus tard serait enregistré à l'heure du rejeu, donc un faux pointage. `PointageRotatifSoignant` n'a aucune file. → §7 Q2 (aucune file ; reçu + réconciliation).
3. **Pauses** : il n'y a pas de `fn_pointer_*_pause` dans le parcours vivant ; une pause est une FERMETURE puis une OUVERTURE de `fn_scanner_code_pointage` (segments `EFFECTIF`, l.55702-55716 et l.55781-55783). **Code de secours** : c'est la saisie manuelle des six chiffres du code rotatif (`PointageRotatifSoignant.tsx` l.215-229) ; `SaisieCodeSecours` (`fn_valider_code_secours` l.64991) relève de ①.
4. **Précision GPS** : `fn_etat_pointage_mission` ne renvoie aucune coordonnée (l.35180-35190) et la FERMETURE n'écrit pas `presences.depart_precision_gps_m` (l.55809-55826). La relecture de précision passe par `scans_pointage.precision_gps_m` (lisible par le soignant, `sp_select` l.79931). « Une présence issue de la coquille » serait une présence de **production** (la coquille 1.0.7 vise `flripxtsyegjshnhzjkz`, et aucun web STAGING n'existe dans le dépôt) : B9 données prod. → §7 Q21.
5. **Le consentement GPS du web est inatteignable** : seul `pointerArrivee` (mort) ouvre `ConsentementGPS` (`PresencesSoignant.tsx` l.369-371, l.541-543). En vivant, un soignant à `consentement_gps IS NULL` pointe sans GPS (`PointageRotatifSoignant.tsx` l.123). Le profil web affiche l'interrupteur coché quand la valeur est NULL (`ProfilSoignant.tsx` l.194 `!== false`). → §7 Q4.
6. **Pas de « PDF serveur » pour les contrats** : `generate-contrat-mission-pdf` stocke du **HTML** (`text/html`) dans le bucket `contrats-signes` (`supabase/functions/generate-contrat-mission-pdf/index.ts` l.7, l.261-262). La preuve signée est le SHA-256 UTF-8 de `contrats_mission.contenu_html` (`fn_signer_contrat_otp` l.56549, contrôles l.56550-56565). PDFKit est sans objet ; le web n'affiche pas un PDF mais le HTML passé par DOMPurify (`ContratMission.tsx` l.633, `src/lib/sanitize.ts` l.3-16). → §7 Q17.
7. **Deux modes de signature existent** : OTP SMS (`SignerContratOtp`) et signature manuscrite (`fn_signer_contrat_soignant` l.56724, sans hash). Pour un compte TEST, le web désactive le SMS et force le canvas (`ContratMission.tsx` l.256-266, l.724). → §7 Q18.
8. **Le dispositif de recette OTP STAGING n'est pas complet** : `scripts/ci/sms-signature-staging.sql` l.1 (« Not a production migration, allocator or activation ») crée `private.signature_sms_test_capacities` et `fn_admission_otp_signature_recette` (l.120-142), mais aucun script du dépôt n'insère de capacité ; l'admission exige un téléphone réel par acteur, `preferences_notifications.canal_sms = true` et un compte Twilio de recette (l.75-116). Le code OTP part par SMS réel : la preuve est de niveau 4/5, avec Gabrielle. → §3 S1, §6, §7 Q20.
9. **`fn_scanner_code_pointage` renvoie au soignant le code suivant** (`nouveau_code`, `nouveau_hmac`, l.55871-55874). Un soignant pourrait fermer un segment hors de l'établissement. Le web l'ignore ; le pilote RN l'écartait explicitement (`mobile-native/src/workflows/presence/supabaseGateway.ts` l.395). → décodeur en liste blanche + PR backend B1 (§7 Q8).
10. **Les refus de pointage sont des exceptions PostgREST**, pas du jsonb : `P0002` (l.55649, l.55775), `42501` « Vous n'êtes pas assigné(e) à cette mission. » (l.55652), `23514` (l.55662, l.55677, l.55686, l.55778), plus les triggers de `presences` à la première OUVERTURE : `fn_exiger_conformite_demarrage_mission` (l.35867-35926, dont `42501` l.35875) et `dec_fenetre_pointage` (`P0001`, l.1961). Avec le mapping du lot 0, `42501` deviendrait « Votre session a expiré » (`SupabaseErrorMapping.swift` l.23, l.52). → interception avant mapping, comme `[CODE DU TRAVAIL]` (§2.4). (corrigé v2) Liste non exhaustive : les triggers de `mission_creneaux` (`trg_no_overlap_creneaux` l.76068, `trg_dec_verrouiller_planning_candidatures` l.75856, `trg_protect_creneaux_facture` l.76232) et `dec_depart_apres_arrivee` (`presences`, l.1570) peuvent aussi lever. Règle : toute `PostgrestError` décodée (réponse PostgREST à corps `{code, message}`) prouve un **rollback** → refus (message verbatim si le SQLSTATE est déclaré pour la RPC, message générique sinon), jamais `.incertain` ; seuls `URLError`, délai `bounded` et `HTTPError` sans corps PostgREST (502/504 de passerelle) sont incertains.

### 2.2 Extension de `Gateways` et ports d'appareil

Même mécanique que le lot 1 (PRINCIPES §2 amendé par T1) : Swift interdit les propriétés stockées en extension, les ports backend du lot 2 sont **ajoutés dans le corps** de `Gateways` avec un défaut « non câblé ».
