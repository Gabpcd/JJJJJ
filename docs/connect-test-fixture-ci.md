# Préparation CI des acteurs Connect TEST

L'opérateur reste fermé : `connect-test-fixture-ci.contract.json` contient `ready:false` et aucun pin. Le workflow manuel s'exécute uniquement sur le SHA main exact demandé, sous le verrou staging commun. Il ne déploie rien et ne crée ni AccountLink, capacité, Checkout, Refund ou transfert. Les trois sources du préparateur doivent d'abord être portées, après revue, sur main avec cet opérateur ; la branche financière peut rester candidate.

Avant l'ouverture du contrat, renseigner explicitement le SHA/arbre de la fixture relue, ses trois SHA256, le run/attempt/job de sa preuve SQL réellement exécutée, la revue, son expiration (moins de quatre heures) et le contrat de préparation : catalogue staging, empreintes des trois Edge, canaux TEST vérifiés. `pgProof.fixtureSqlReviewed:true` atteste la revue du contenu de cette preuve, pas simplement un job vert. Le runner relit la réussite du run/job du SHA exact et compare les trois fichiers distants avec leurs octets locaux. Le SHA main d'exécution est fixé séparément par `expected_main_sha`, évitant qu'un fichier versionné prétende contenir son propre SHA. Le préparateur continue à relire ce main exact avant chaque effet.

Créer localement une paire RSA4096 éphémère, conserver la clé privée en fichier `0600`, et transmettre uniquement la clé publique PEM et son SHA256 SPKI DER dans les deux inputs destinataire. Ne jamais fournir une clé privée à GitHub. Les tests Node et le contrôle fermé précèdent l'unique étape qui reçoit les accès Supabase/Stripe TEST. Aucun npm, navigateur ou build n'est lancé par ce job.

Le préparateur crée les identifiants synthétiques dans le runner. Chaque intention et reçu est écrit en privé dans `RUNNER_TEMP`, puis chiffré AES-256-GCM avec une clé enveloppée RSA-OAEP-SHA256 pour le destinataire local, avant de poursuivre. Seuls `fixture.encrypted.json` et un résumé de booléens sont publiés, pendant un jour. Le journal ne contient jamais les clés de service, Management, Stripe ni les sessions Auth. Les credentials S/E de recette sont uniquement dans le journal chiffré. Télécharger ce petit artefact, vérifier son run et conserver son SHA256, puis ouvrir localement :

```sh
node scripts/ci/connect-test-fixture-ci.mjs open CHEMIN_ENVELOPPE CHEMIN_CLE_PRIVEE SHA256_ENVELOPPE SHA256_DESTINATAIRE DOSSIER_PRIVE_NEUF
```

Cette commande hors réseau écrit `journal.private.json`, `manifest.private.json` et `frontend.private.json` en `0600`, sans afficher les identifiants. Le dernier fichier contient les deux comptes S/E, les identifiants des pièces et objets TEST et l'URL staging ; aucune clé CI et aucun credential admin. Le navigateur peut alors se connecter à ces deux comptes sur le frontend candidat configuré pour staging. L'onboarding Express via AccountLink opérateur, la lecture du statut dans Jolene, l'allocation bornée et paiement → confirmation → remboursement restent des opérations séparées.

Le job refuse les reruns et un second dispatch du même SHA main. Après réponse incertaine ou interruption, conserver et déchiffrer le dernier journal, rapprocher l'intention existante ; ne pas relancer une nouvelle fixture pour masquer l'incertitude. Le journal chiffré est sauvegardé à chaque checkpoint et l'upload s'exécute aussi après échec. Une coupure avant le tout premier checkpoint ne peut pas avoir créé d'acteur. Une coupure de runner peut empêcher l'upload : ce cas exige un rapprochement, jamais une recréation automatique. Ne pas relancer le préparateur après l'onboarding ou l'allocation de capacité, dont les états sortent volontairement de son contrat.

Les tests du wrapper emploient des transports simulés et vérifient les refus, le chiffrement, les checkpoints et l'absence de clés CI dans l'enveloppe. Ils ne prouvent ni le SQL de la fixture ni le parcours fournisseur. La recette réelle doit ensuite conserver les preuves frontend et rapprocher les mêmes objets Stripe TEST, sans production ni livraison mobile.
