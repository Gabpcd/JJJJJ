# Suppression du profil avec historique financier

Le parcours monté Profil soignant → Confidentialité appelle l’Edge `delete-account`, puis `fn_supprimer_compte_rate_limited()` et `fn_supprimer_mon_compte()`. La dernière routine tentait de remplacer `soignant_id` par NULL dans `stripe_transfers` puis `paiements_soignant`. Les deux colonnes sont déjà NOT NULL. Une ligne historique suffit donc à faire échouer la transaction avant son reçu privé ; le contrôle de protection des transferts peut aussi refuser l’écriture plus tôt. Il s’agit d’un défaut antérieur à la nouvelle garde d’immutabilité des paiements.

Les définitions, propriétaires, ACL, configurations, deux contraintes et deux lignes d’inventaire ont été relus en production et staging le 1er octobre 2026, sans donnée de compte. Les deux environnements avaient les mêmes corps : `fn_supprimer_mon_compte()` = `71254d2065c67c11ce0460368f20d01f` et wrapper = `f283e828e173bf12d8f633be28431c97`. Les relevés locaux sont conservés dans `/private/tmp/jolene-suppression-historique-revue-20261001`. Ils ne sont pas un export DDL de production vers GitHub.

La migration retire uniquement ces deux UPDATE et distingue ces tables conservées dans l’audit. Les UUID, parties, montants et références de paiements/transferts restent inchangés et continuent à pointer vers le profil anonymisé, déjà conservé par le fonctionnement existant. Elle ne change ni les NOT NULL, ni les ACL, ni les refus de missions futures/en cours, ni les règles de conservation. Le wrapper, le reçu privé et l’Edge qui effectue ensuite le soft-delete Auth sont inchangés. Le nouveau corps vaut `f3af23aeeb4e30aba07e422c0e819aeb` ; la migration vérifie corps complet, propriétaire, ACL, configuration et inventaire avant/après. Elle actualise uniquement l’empreinte d’inventaire de cette routine, sans changer sa catégorie, justification ou date.

## Témoin préparé, sans exécution métier

`suppression-compte-historique-financier.test.sql` est ajouté après le témoin PSC existant. Sous BEGIN/ROLLBACK, cinq identités Auth sont insérées directement en SQL avec des emails `.invalid`, trois profils soignants TEST et un établissement TEST. Aucun endpoint Auth, Storage, Stripe ou autre fournisseur n’est appelé. Les IDs réservés commencent par F161 ; les UUID techniques générés restent liés à ces fixtures. Les missions historiques sont préparées par l’INSERT de maintenance futur déjà permis puis par leur planning passé de 4 h ; cela ne prouve pas une clôture utilisateur.

Les deux histoires réussies couvrent un paiement manuel confirmé par la vraie RPC et un paiement Stripe confirmé avec une trace acquise entièrement synthétique. Le vrai wrapper est ensuite appelé sous le rôle authenticated de chaque soignant. Les lignes complètes de paiement et transfert doivent rester identiques, le profil doit être anonymisé, le reçu privé et l’audit exact doivent exister, et le deuxième appel doit être idempotent. Les factures restent identiques sauf `updated_at` : le no-op historique sur leur `soignant_id` et son trigger d’horodatage/audit restent inchangés. Le témoin vérifie aussi le refus anon, le refus sans profil, le refus d’une mission future sans anonymisation partielle, les contextes restaurés, les tiers intacts et les lignes Auth intégralement inchangées par la RPC SQL.

Les canaux des comptes TEST sont fermés, `defacto_opt_in`, SMS, Chorus et urgence restent désactivés ; aucune qualification, mandat ou signature n’est fabriqué. Les triggers restent actifs. Le test refuse un cron actif, un trigger Auth INSERT ou des contextes de contournement, ainsi qu’une file pg_net initialement non vide ; il exige que cette file demeure vide. Des audits, préférences, notifications ou emails internes peuvent être créés puis supprimés par les triggers et la suppression, mais restent invisibles aux autres transactions et sont annulés. Le test n’exécute ni le soft-delete Auth ni une suppression de Storage/fournisseur.

Le contrôleur indépendant lit avant la transaction puis après succès ou échec les empreintes des deux routines/droits, des triggers et de l’inventaire, ainsi que 24 compteurs couvrant la fixture et ses effets attendus. Il impose zéro résidu F161, zéro requête pg_net en attente et une égalité stricte des deux réponses. Il n’autorise que le staging configuré, sans redirection/retry ni copie de données personnelles. Les tests Node du contrôleur ne font aucun réseau. Le raccord garde les suites existantes et le verrou staging commun ; aucun nouveau dispatch ni secret n’est ajouté.

## Limites et vérifications restantes

Cette livraison source n’est pas une preuve d’exécution SQL. Il faut obtenir le témoin rouge sur l’ancien corps, le passage sous migration candidate et le SELECT indépendant après rollback, puis la revue du résultat exact de CI. Il faut également rejouer la simulation existante `e2e/recette-complete-notation-suppression.spec.ts` pour les rôles concernés sur cinq formats : annulation, refus/erreur temporaire, reprise, attente, résultat et rechargement. Le produit frontend n’est pas modifié par ce lot. Les tests du handler `delete-account-anonymisation.test.ts` doivent rester verts pour son contrat de reçu préalable et de soft-delete.

Une simulation ou une trace Stripe SQL ne certifie ni un paiement fournisseur, ni la suppression Auth réelle. Aucun compte cloud n’a été supprimé, aucun SQL métier exécuté, aucun déploiement ni livraison mobile effectué pour cette préparation. Le parcours reste ouvert jusqu’aux preuves prévues ; ce lot ne permet pas de déclarer une préparation nationale complète.
