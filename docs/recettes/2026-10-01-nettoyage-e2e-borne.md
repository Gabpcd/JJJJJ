# Nettoyage du témoin empêchement — base main 58fd

La campagne connectée 36903142674 / job 110506959274 a échoué sur un timeout du nettoyage afterEach puis afterAll. Les assertions métier du cas « déclaration structurée : preuve, clôture originale et assigné conservé » ne présentent pas d’échec ; la reprise a réussi. Le bilan reste 317 tests réussis, 13 ignorés et 1 flaky, donc campagne rouge avec failOnFlakyTests inchangé.

La première tentative n’a pas de trace (configuration on-first-retry). La trace du retry vert mesure 5,663 s pour afterEach et n’instrumente pas les requêtes Supabase. Il n’est donc pas démontré quel appel distant s’est suspendu ni qu’un verrou PostgreSQL en soit la cause. Aucun appel SQL de diagnostic ou nettoyage distant n’a été exécuté pour ce correctif.

Le défaut reproductible du harnais est distinct : expirer un hook Playwright n’annule pas son fetch Supabase. afterAll peut alors relancer le même nettoyage pendant que la requête précédente continue. Seul le dernier RPC de purge possédait déjà sa propre borne 25 s ; les lectures/suppressions précédentes et le nettoyage Auth n’étaient pas couverts.

Le nouveau contexte asynchrone est activé uniquement autour des nettoyages de cette suite. Il annule les requêtes admin après 25 s, conserve les signaux préexistants, couvre la lecture du corps après les en-têtes et refuse les requêtes suivantes dans le contexte expiré. Il attend la fin du callback, sans Promise.race détachant le travail. Une expiration reste une erreur portant la dernière méthode/table ou RPC, sans filtre/UUID/corps/secret. Les restaurations, droits, filtres, ordre des opérations et assertions sont inchangés. Hors ce contexte, le fetch admin reçoit les arguments originaux. Les délais Playwright 30 s, les retries et failOnFlakyTests restent inchangés.

Vérification locale : 14 tests ciblés verts (7 nouveaux sur le contexte et 7 du nettoyeur existant), typage ciblé helper/client/tests vert. Témoin Playwright sans navigateur ni réseau : ancien hook borné 100 ms pour reproduire rapidement la mécanique → requête encore active et maximum 2 appels concurrents ; contexte corrigé avec sa vraie borne 25 s et hook 30 s → erreur précise conservée, zéro appel actif, maximum 1, afterAll réussi. Les deux processus du témoin sortent volontairement 1 puisque la panne de transport reste un échec ; le contrôleur vérifie les erreurs et compteurs exacts. Il ne prétend pas qu’une coupure réseau est réparée.

Preuves locales : /private/tmp/jolene-cleanup-e2e-preuves-20261001, journaux ciblés main conservés dans /private/tmp/jolene-numerotation-integration-preuves-20261001. Revue indépendante source des quatre fichiers effectuée par Info avant gel. Le premier essai du test unitaire sous environnement Node a révélé le setup global window incompatible ; le test rejoint l’environnement jsdom existant sans modifier ce setup.

Limites : ce correctif empêche le chevauchement client et rend un futur blocage diagnostiquable. Il ne garantit pas qu’un abort HTTP annule une transaction déjà engagée sur le serveur. La nouvelle campagne connectée doit encore prouver le nettoyage distant normal ; aucun vert de simulation/provider ni correction d’un SQL métier n’est revendiqué.
