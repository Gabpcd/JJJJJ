## CI après installation et clôture de la cohorte

Le staging réel ne doit pas être remis à zéro pour rejouer la PR. Le job conserve le témoin PostgreSQL 17 neuf, puis reconnaît en lecture seule l'installation déjà présente : unique migration ajoutée Connect, mêmes octets migration/table/admission que le contrat installé, catalogue et registre exacts `expectedAfter`, delta Connect identique au témoin frais. Il exige une seule capacité révoquée, une seule opération REFUND/SUCCEEDED sans bail ni revue, cohorte TEST connue, trace sans transfert et barrières/queues fermées. Une installation partielle ou divergente refuse ; elle ne bascule jamais vers un bootstrap.

Pour ce seul état vérifié, le job conserve toutes les régressions SQL sous ROLLBACK et omet seulement la réapplication de la migration déjà installée et le bootstrap main. Une nouvelle lecture indépendante compare toutes les empreintes de données, y compris la cohorte, même si la réponse de transaction a été perdue. Les empreintes supplémentaires des droits par défaut et des séquences prouvent leur conservation pendant ce run ; elles ne prétendent pas correspondre à une ancienne référence qui n'en contenait pas. Une séquence avancée malgré rollback fait échouer le contrôle, sans reset ni remise à zéro. L'artefact `connect-installed-catalogue-proof` reste distinct de l'ancienne preuve d'installation annulée. Si les trois tables sont absentes, le chemin staging vierge existant reste inchangé. Aucun accès Stripe ni changement de runtime financier n'est introduit.

Ce mode ne concerne que la PR ajoutant cette migration Connect. Après fusion, `sql-transaction` ne s'exécute pas sur le push main ; le déploiement existant reste inchangé. Les PR suivantes qui ont déjà cette migration dans leur base utilisent le chemin général, sans reconnaissance installée implicite. Les lectures complètes exigent `current_user=postgres`, une transaction READ ONLY et `row_security=off` : une politique qui filtrerait la lecture fait refuser le constat, sans étendre de privilège. Comme le lecteur de préparation fixture existant, le transport emploie `read_only:false` pour conserver le rôle opérateur déjà autorisé : le drapeau Management API sélectionnerait son rôle restreint. Le caractère non modifiable est imposé dans PostgreSQL par `BEGIN READ ONLY`, vérifié dans le snapshot ; le témoin PG17 doit refuser une écriture ajoutée après le vrai SELECT avec SQLSTATE `25006`. Aucun GRANT, changement de rôle, réessai ou repli après un refus n’est ajouté.

## Correction après revue indépendante

Le handler configuré refuse maintenant une trace historique sans Session, même si la capacité n'a pas encore de Session non plus. Toute trace doit correspondre exactement à l'opération, la Session et l'identifiant de trace de la capacité. La reprise d'une Session ouverte déjà liée se fait uniquement en lecture : aucune expiration, reprise de trace ou remise à zéro après quinze minutes. Une Session liée expirée ou complète demande un rapprochement.

Avant toute réservation nouvelle, le handler pagine les Sessions Stripe et refuse celles de cette FH/commission qui ne sont pas déjà liées à sa capacité, y compris expirées. Il refuse également les claims historiques ; cette dernière précondition est reproduite dans le RPC SQL TEST. Une commission absente ne déclenche pas de génération implicite. La destination est effectivement relue chez Stripe : identifiant, propriétaire `metadata.soignant_id`, capacités et disponibilité doivent correspondre.

Le nouveau fichier `stripe-connect-staging-pay-runtime.test.ts` exécute le vrai handler configuré et ses helpers, avec transports en mémoire : 38 scénarios réussis, portant le sous-ensemble runtime à 124 tests verts. Ils couvrent la création, la reprise exacte, les traces/claims/Sessions historiques, la pagination et la disponibilité réelle attendue du destinataire. Ils ne remplacent toujours ni l'exécution PostgreSQL 17 ni le circuit Stripe TEST dans l'interface.

Le contrôle des traces cherche aussi une autre trace de la FH **ou de la commission**, sans se limiter à la plus récente. La reprise liée exige un claim présent et exact. Le RPC inscrit `claim_reserved_at` dans la même transaction que son claim neuf, sous le verrou existant de la ressource : une réponse perdue avant la réservation de l'opération peut être reprise sans confondre ce claim neuf avec un ancien. Le témoin PG17 contient ce scénario mais reste à exécuter. Les tests Node du supplément sont maintenant au nombre de 42.
