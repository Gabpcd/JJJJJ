# Reprise SQL-only de l'installation SMS staging

Le run `38629072392` a déployé le send-sms attendu en version 24, puis l'aperçu SQL a échoué avant la DDL : `postgres` ne peut pas prendre un verrou SHARE sur `cron.job`, qui appartient à un autre rôle et lui accorde seulement SELECT. Le reçu original reste incertain ; aucune relance de cet installateur n'est prévue.

Cette reprise vérifie la version 24 déjà présente et ses six sources exactes. Elle n'appelle aucune CLI de déploiement et ne modifie aucun secret ni rôle. Les 36 autres verrous, le rendu SQL produit, les contrôles d'absence, la capacité vide, les métadonnées des routines, les empreintes métier et les prédicats de calme restent ceux de l'installateur initial. Seul le verrou `cron.job` devient ACCESS SHARE, séparé ; cette table reste dans les snapshots avant/après. Ce mode ne bloque pas ses écritures concurrentes. Le manifeste et le reçu nomment cette observation explicitement.

Le manifeste est encore `ready=false`, avec `recoveryCi=null`. Il refuse toute exécution avant credentials tant que le témoin CI et la revue ne sont pas épinglés. Il ne faut pas relancer le workflow initial ni remplacer son contrat de version 23.

Le workflow `sms-install-sql-only-pg17.yml` ne possède aucun secret de staging. Il utilise PostgreSQL 17.6 éphémère, avec `sms_fixture_admin` comme bootstrap OID10. Il crée un login `postgres` distinct, monte les routines réellement possédées par postgres, puis une nouvelle session admin retire SUPERUSER à ce login et lui donne BYPASSRLS. Le témoin vérifie avant/après que le login postgres n'est pas OID10 et reste `NOSUPERUSER BYPASSRLS` pendant les transactions testées. `cron.job` appartient à un autre rôle avec SELECT seul et RLS. Le témoin exige le refus historique 42501, puis la transaction complète de reprise, la capacité vide fermée et le retour exact après ROLLBACK. Les cinq routines et le rendu sont épinglés ; les annexes des tables observées sont réduites. Ce banc ne prouve pas le catalogue staging intégral, le moteur pg_cron, un fournisseur, le frontend ou un appareil.

Les tests purs locaux passent : 15 tests Node et 8 tests Python, sans test ignoré, avec `/Applications/Xcode.app/Contents/Developer/usr/bin/python3` (Python 3.9.6). Ce runtime dispose déjà de pglast ; la commande `/Applications/Xcode.app/Contents/Developer/usr/bin/python3 -B -m unittest discover -s tests/python -p test_sms_install_sql_only_witness.py` analyse aussi le SQL/PLpgSQL complet. Le test CLI exige un code de sortie 1 et un reçu fermé après refus de préflight, avec PATH vide. Le `python3` de CI peut ignorer le seul test de parsing optionnel si pglast est absent ; le workflow exécute ensuite réellement PostgreSQL 17. Aucun PostgreSQL ou conteneur local n'a été lancé.

Le premier témoin distant `38635919330` a échoué au montage, avant les six cas : l'ancien banc tentait de démoter le bootstrap OID10, opération interdite par [PostgreSQL 17.6](https://github.com/postgres/postgres/blob/REL_17_6/src/backend/commands/user.c#L819-L827). Le reçu conserve `completed=false`, SQLSTATE 0A000 et nettoyage après échec confirmé. Le bootstrap distinct corrige ce banc seulement ; son nouveau résultat PostgreSQL réel reste à produire en CI distante.

Après revue et CI, le manifeste pourra épingler run, job, commit exécuté et artefact du témoin. L'opérateur compare les blobs de tous les fichiers critiques avec l'arbre CI. Le manifeste de reprise lui-même est exclu de cette liste pour permettre l'ajout de ces références après le témoin ; son contenu et son digest doivent être revus séparément. Toute dérive du code, du produit, de la version Edge, du projet ou des snapshots ferme le parcours.

Le workflow manuel `resume-sms-staging-sql-only.yml` reste protégé par main exact, tentative unique, contexte GitHub et concurrence commune des écritures staging. Après un aperçu annulé et un readback identique, il peut effectuer un commit unique puis un readback fermé. Un résultat perdu ou refusé n'est jamais rejoué. Le reçu fsync conserve les empreintes initiales de cette reprise, son périmètre `CURRENT_RECOVERY_ONLY`, et le statut HTTP avec libellé d'endpoint fermé. Il ne contient ni réponse brute, ni SQL, ni token. Aucun invariant métier rétroactif du run original n'est revendiqué, car son snapshot initial n'a pas été conservé.

La sécurité install-only ne valide aucun envoi : capacité vide, aucun acteur alloué, aucune activation, aucun appel fournisseur. La fermeture normale staging de send-sms est vérifiée par ses sources exactes. Les parcours frontend en simulation, l'intégration SMS réelle TEST et les appareils physiques restent des vérifications distinctes.
