# Reprise SQL-only de l'installation SMS staging

Le run `38629072392` a déployé le send-sms attendu en version 24, puis l'aperçu SQL a échoué avant la DDL : `postgres` ne peut pas prendre un verrou SHARE sur `cron.job`, qui appartient à un autre rôle et lui accorde seulement SELECT. Le reçu original reste incertain ; aucune relance de cet installateur n'est prévue.

Cette reprise vérifie la version 24 déjà présente et ses six sources exactes. Elle n'appelle aucune CLI de déploiement et ne modifie aucun secret ni rôle. Les 36 autres verrous, le rendu SQL produit, les contrôles d'absence, la capacité vide, les métadonnées des routines, les empreintes métier et les prédicats de calme restent ceux de l'installateur initial. Seul le verrou `cron.job` devient ACCESS SHARE, séparé ; cette table reste dans les snapshots avant/après. Ce mode ne bloque pas ses écritures concurrentes. Le manifeste et le reçu nomment cette observation explicitement.

Le manifeste est réarmé uniquement pour l’installation SQL vide et fermée après revue du nouveau témoin PostgreSQL 17 `38684822564`, job `116257166236`, head `763bf5e8fe5e93b116c9a531fb666a4a326f7991`, commit exécuté `7ac810ee511d437eb4252d7086deb606a29b51fa`. Les six cas ont réussi et le nettoyage est confirmé. L’artefact `11948694907` est épinglé par son SHA-256 ZIP `f9b795f844a40e236a9979740fd1ca4112eeff214f1c5bc03763073792e681c5` ; les 44 blobs critiques correspondent exactement à l’arbre exécuté. Le digest du manifeste est recalculé après ces références. Les bornes restent `installationOnly=true`, `capabilityEnabled=false`, `deploymentAllowed=false`. Ce correctif n'autorise aucun replay de la reprise ni du workflow initial et ne remplace pas le contrat historique de version 23.

Le workflow `sms-install-sql-only-pg17.yml` ne possède aucun secret de staging. Il utilise PostgreSQL 17.6 éphémère, avec `sms_fixture_admin` comme bootstrap OID10. Il crée un login `postgres` distinct, monte les routines réellement possédées par postgres, puis une nouvelle session admin retire SUPERUSER à ce login et lui donne BYPASSRLS. Le témoin vérifie avant/après que le login postgres n'est pas OID10 et reste `NOSUPERUSER BYPASSRLS` pendant les transactions testées. `cron.job` appartient à un autre rôle avec SELECT seul et RLS. Le témoin exige le refus historique 42501, puis la transaction complète de reprise, la capacité vide fermée et le retour exact après ROLLBACK. Les cinq routines et le rendu sont épinglés ; les annexes des tables observées sont réduites. Ce banc ne prouve pas le catalogue staging intégral, le moteur pg_cron, un fournisseur, le frontend ou un appareil.

Les tests Node ciblés vérifient les codes des refus importés, la sauvegarde du diagnostic avant refus, sa projection publique bornée et le blocage en cas d'échec du checkpoint. Ils utilisent uniquement des transports simulés ; aucun PostgreSQL, navigateur, fournisseur ou conteneur local n'est nécessaire. Le témoin PostgreSQL 17 décrit ci-dessus reste une vérification séparée.

Le premier témoin distant `38635919330` a échoué au montage, avant les six cas : l'ancien banc tentait de démoter le bootstrap OID10, opération interdite par [PostgreSQL 17.6](https://github.com/postgres/postgres/blob/REL_17_6/src/backend/commands/user.c#L819-L827). Le reçu conserve `completed=false`, SQLSTATE 0A000 et nettoyage après échec confirmé. Le bootstrap distinct corrige ce banc seulement. Le [témoin PostgreSQL 17 suivant](https://github.com/Gabpcd/JJJJJ/actions/runs/38638713994), job `116108443756`, a réussi les six cas avec `completed=true` et nettoyage confirmé. Il a exécuté `eb356b6e11987647696ee08589e620fe53977133` depuis le head `f26e81df15cea00313aff42ff08631bbebb07001`. L'artefact `sms-install-sql-only-pg17-public`, ID `11928947715`, est épinglé par son SHA-256 ZIP `5939490d5de2a501acc8958a74e2cd8a043ba8ec88f7469aac045db781bc7e37`. Cette preuve concerne la base CI éphémère, aucune installation staging ni aucun envoi SMS.

Le manifeste épingle run, job, commit exécuté et artefact de ce nouveau témoin après revue indépendante. L'opérateur compare les blobs critiques avec l'arbre CI ; l'intégration d'autres préparations doit conserver ces blobs exacts. Le manifeste de reprise lui-même est exclu de cette liste pour permettre l'ajout de ces références après le témoin ; son contenu et son digest sont revus séparément. Toute dérive du code, du produit, de la version Edge, du projet ou des snapshots ferme le parcours.

Le workflow manuel `resume-sms-staging-sql-only.yml` reste protégé par main exact, tentative unique, contexte GitHub et concurrence commune des écritures staging. Après un aperçu annulé et un readback identique, il peut effectuer un commit unique puis un readback fermé. Un résultat perdu ou refusé n'est jamais rejoué. Le reçu fsync conserve les empreintes initiales de cette reprise, son périmètre `CURRENT_RECOVERY_ONLY`, et le statut HTTP avec libellé d'endpoint fermé. Avant chacun des six contrôles de snapshot, il sauvegarde son numéro, sa phase, des indicateurs de forme, `quiet/absent/closed`, le nombre de routines et les seules empreintes MD5 d'invariants et de cibles. Les compteurs de lignes et de routines sont plafonnés respectivement à 2 et 32, avec indicateur de plafonnement ; les valeurs inattendues ne sont jamais recopiées. Les refus du helper et de la reprise partagent la même classe et conservent leur code. Le reçu ne contient ni réponse brute, ni métadonnée de routine, ni SQL, ni token. Aucun invariant métier rétroactif du run original n'est revendiqué, car son snapshot initial n'a pas été conservé.

La sécurité install-only ne valide aucun envoi : capacité vide, aucun acteur alloué, aucune activation, aucun appel fournisseur. La fermeture normale staging de send-sms est vérifiée par ses sources exactes. Les parcours frontend en simulation, l'intégration SMS réelle TEST et les appareils physiques restent des vérifications distinctes.

La tentative précédente `38664524904` sur main `3a8c5c67be2defd6a12b843c4e1d46bc43a6c77a` s’est arrêtée en baseline avant aperçu SQL ou commit. Le deuxième snapshot n’avait pas été conservé et son refus importé avait été masqué. Elle ne permet pas de reconstruire le refus exact historique. Cette tentative n’est pas rejouée ; toute nouvelle exécution exige une intention distincte sur le nouveau main relu, avec ces diagnostics persistés.
